# Требования MVP

## 1. Назначение

Создать сервис локального перевода текста, который используется другими внутренними приложениями через HTTP API и не зависит от платных или квотируемых API перевода.

Основной текущий сценарий: перевод английского текста на русский для автоматического импортера контента. Архитектура при этом не должна быть жёстко ограничена парой `en -> ru`.

## 2. Главные требования

### FR-001. Локальный inference

Перевод должен выполняться локально. Пользовательский текст не должен отправляться
внешним сервисам. Загрузка публичных моделей и служебных файлов при startup или
первом запросе допустима и не должна включать пользовательский текст.

### FR-002. HTTP API

Сервис предоставляет JSON HTTP API.

### FR-003. Минимальный запрос

Для перевода обязательны только:

- `text`;
- `target_language`.

Пример:

```json
{
  "text": "Hello world",
  "target_language": "ru"
}
```

### FR-004. Язык исходного текста по умолчанию

Если `source_language` не передан, использовать конфигурационное значение `DEFAULT_SOURCE_LANGUAGE`.

Для MVP значение по умолчанию: `en`.

Автоматическое определение языка не требуется в MVP.

### FR-005. Переводчик по умолчанию

Если `translator` не передан, использовать `DEFAULT_TRANSLATOR`.

Для MVP: `argos`.

### FR-006. Выбор движка

Клиент может явно передать поле `translator` и выбрать зарегистрированный provider.

### FR-007. Параметры движка

Клиент может передать объект `translator_params` с параметрами выбранного provider.

Основной API не должен зависеть от набора параметров конкретного движка.

### FR-008. Первый provider

Первый production provider — Argos Translate.

### FR-009. Расширяемость

Добавление Marian/CTranslate2, Ollama или другого локального provider не должно требовать изменения основного endpoint `/v1/translate`.

### FR-010. Список переводчиков

API должен позволять получить список зарегистрированных переводчиков и их состояние.

### FR-011. Health endpoints

Должны существовать отдельные проверки:

- liveness приложения;
- readiness для обслуживания запросов перевода.

### FR-012. Авторизация

В MVP авторизация отсутствует.

Архитектура не должна намеренно препятствовать добавлению API-key/auth middleware позднее.

## 3. Нефункциональные требования

### NFR-001. Стабильный контракт

Внутренние детали библиотек перевода не должны протекать в публичный API.

### NFR-002. Предсказуемые ошибки

Все прикладные ошибки возвращаются в едином JSON-формате с машинным кодом.

### NFR-003. Наблюдаемость

Минимально логировать:

- request id;
- выбранный translator;
- source/target language;
- длину текста;
- длительность перевода;
- результат операции.

По умолчанию полный исходный текст и полный перевод в production-логи не писать.

### NFR-004. Ограничение размера

Максимальная длина `text` должна быть конфигурируемой.

Предлагаемый default: 20 000 Unicode characters.

### NFR-005. Timeout

Максимальное время одного перевода должно быть конфигурируемым.

Предлагаемый default: 30 секунд.

### NFR-006. Независимость от платных и квотируемых сервисов

Сервис не должен использовать API, стоимость или доступность которых зависит от
количества переводов. Сетевые загрузки публичных моделей и служебных файлов
разрешены, в том числе в runtime.

### NFR-007. Тестируемость

Контракт API должен тестироваться без установленной реальной ML-модели.

## 4. Что НЕ входит в MVP

- пользователи и роли;
- API keys/JWT/OAuth;
- биллинг;
- база данных;
- история переводов;
- web UI;
- очередь задач;
- asynchronous jobs;
- batch endpoint;
- streaming;
- автоматическое определение языка;
- автоматический fallback на другой translator;
- кэширование переводов;
- внешние DeepL/Google/Yandex API.

## 5. Configuration

Минимальный набор environment variables:

```text
APP_HOST=0.0.0.0
APP_PORT=8000
LOG_LEVEL=INFO
DEFAULT_TRANSLATOR=argos
DEFAULT_SOURCE_LANGUAGE=en
MAX_TEXT_LENGTH=20000
TRANSLATION_TIMEOUT_SECONDS=30
```

При необходимости provider может иметь собственный namespace переменных, например `ARGOS_*`, `MARIAN_*`, `OLLAMA_*`.

## 6. Языковые коды

Во внешнем API MVP использовать короткие ISO 639-1 codes там, где они доступны: `en`, `ru`, `de`, `fr` и т. п.

Provider adapter отвечает за преобразование публичного кода в собственный формат конкретной модели, если это потребуется.

## 7. Критерий успешности MVP

Клиент может запустить сервис локально и выполнить:

```bash
curl -X POST http://localhost:8000/v1/translate \
  -H 'Content-Type: application/json' \
  -d '{"text":"Hello world","target_language":"ru"}'
```

При доступной Argos-модели `en -> ru` сервис возвращает перевод и метаданные, а клиенту не нужно знать ничего о Python API Argos Translate. Сам inference выполняется локально и не расходует внешнюю квоту на запросы.
